# CoEvo 科研软件工作规范

当前职责说明：本文件的数据对象、记录结构或工程约定继续复用；实验场景、模型、学习配方和评价以[当前研究导航](当前研究导航.md)链接的职责文档为准。此前版本编号及任务路线用于追溯，不覆盖最新研究定位。

日期：2026-10-13。本文规定工程工作方式，不重定义现行研究方案与评估协议的实验因素、数据准入、指标或推断标准。当前已有 Python 包、依赖锁、CPU 检查和活动 Agent 补丁；完成一次指定 128K 资格与真实 LoRA 更新试跑，候选旧任务退化、未晋升，历史试跑曾暂停；用户已授权 T00–T04 基础建设，尚无正式科研收益。实际边界见 [研究快照](../experiments/workstation-rsi/review_snapshot.md)。工程要求按实际阶段落实，不能据目录和配置声称后端验收已完成。

## 1. 质量目标与减法原则

开发优先推进可运行系统与有信息价值的实验，避免在审计、重复验证和防御性自锁研究上消耗大量时间。检查针对当前变更、已观察故障和影响科学结论的关键契约，范围与阶段相称；相关检查通过后继续开发。只有新变更、失败或具体未解问题才扩大验证，不为假想风险反复审计、增设审批或要求先建完整验证体系。探索性闭环不以正式确认实验的全部验收为前提，正式结论仍需相应数据隔离与对照证据。

采用适合本项目的轻量科研软件规范：单仓库、短分支和自动检查支撑开发，实验协议版本、数据来源及模型发布记录支撑研究。首要标准是可追溯性，每项结果都能定位到代码、完整配置、数据、模型、环境和评价依据。

以合理、合适、充分且可维护为目标，不以压缩到最少功能、文件或样本为目标。实现范围由科学问题、实际使用和验收证据决定；验证规模由错误风险、统计精度和资源预算决定。试点用于发现问题和校准，不替代正式验证。

新增抽象、依赖、后端或兼容层前，说明它解决的实际问题、使用者与验证方式。无实际使用者的旧接口、重复实现、猜测性 fallback 和无法验证的兼容代码应移除；失败须明确暴露，不能静默切换模型、后端或评价路径。支持范围改变时记录受影响使用者和实验。保留历史版本与重建材料即可支持旧实验复核，不要求现役代码永久兼容全部历史配置。

不以徽章、目录数、强制提交格式或统一覆盖率门槛判断质量。也不因追求减法删掉必要的对照、数据隔离、失败记录或运行证据。

## 2. 本机工作与代码组织

工作站为阶段 A–C 主实验平台，承担 Agent 推理、128K+ 资格、数据生成、训练与周期评价；笔记本最终部署后移到阶段 D，日常研究开发仍可在任一机器推进。冷文件优先放 `/mnt/e/CoEvo/` 并链接到项目，活动代码与执行环境按实际性能保留 Linux 文件系统。本机核心状态、筛选和指标测试应能在无 GPU、无工作站连接的条件下运行；模型能力与真实后端验收另行安排。

采用单仓库，按职责复用实现。实施修订 `workstation-128k-2026-10-13` 优先复用开源运行基础、成熟任务/检查器和独立训练组件。A–D 保留为设备与工程阶段；当前科学实验使用研究 I（I-A/I-B）、II、III（III-A/III-B），旧 E0/E1/ER/ET/EC/EL 仅用于历史材料。具体定义引用[研究方案](agent_model_coevolution_experiment_plan_v0.5.md)。实验目录调用共享模块，不复制 Agent、训练器或指标实现。

研究平台、被研究 Agent、独立任务环境、学习模块和评价模块按职责分离，无须拆为五套服务。`rsi.py` 保持调度职责，数据准入、训练、状态和评价逻辑复用共享模块。当前沿用已实测的 Pi SDK，先扩展真实任务所需能力；T00–T09 及交付依据见[任务路线](07_项目现状与任务路线_2026-10-13.md)。独立任务场景不默认使用 CoEvo 开发仓库，研究助手修复必须与学生结果区分。

| 位置 | 职责与边界 |
|---|---|
| `src/coevo/` | Python 可安装实现；按实际需要组织 contracts、state、tools、selection、training、evaluation、adapters |
| `scripts/` | 运行薄封装，核心逻辑保留在包内 |
| `configs/` | 版本化的运行、训练和评价配置 |
| `experiments/<study_id>/` | 冻结单、配置引用、允许公开的清单与结果报告 |
| `tests/` 与 `examples/` | 无私人信息的合成样例、局部/集成/行为回归验证；不含 H 数据与答案 |
| `data/`、`artifacts/`、`runs/` | 版本控制外的本地数据、权重与完整轨迹；受控或外部存储按实际情况选择 |
| `docs/` | 现有职责文档及确有必要的决策说明 |

目录在有实际内容时创建。公开产物索引统一放入 `experiments/`，避免与被忽略的 `artifacts/` 混放。选定 Agent 的扩展确需 TypeScript 时才增加对应目录和锁文件；momo-code 的 Bun/TypeScript 与 Python 研究组件分别固定实际依赖，不重写上游会话、工具、任务运行器或训练基础设施；允许修订 momo-code 的模拟路径为独立本地训练与真实评价接口；仅在已证实的依赖冲突或独立部署需求下拆分环境。

Python 采用 `src/` 布局，开发时安装项目，并验证构建 wheel 后在干净环境、源码目录外安装和运行，检查必要资源是否包含。该布局帮助发现开发源码与安装产物的差异。[PyPA 布局说明](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)

复用前固定上游 commit/revision，登记模块路径与 hash、接口契约、许可文件、保留/替换决定和实际验收证据。可直接依赖时优先依赖与薄适配；必须修改时保留可追溯补丁，不复制整套服务。momo-code 的 LICENSE 与 USE_RESTRICTIONS.md 同时存在，RSIGym 本次根目录清单未见许可证，具体复制、修改和再分发范围待厘清；核查不明确不阻塞独立数据契约、任务脚本和训练适配设计。状态和行为 correctness 测试覆盖自研适配与研究契约，复用组件的已知正确/错误任务仍须本地验收。模拟数据只用于明确标识的工程 fixture，不能进入真实评价、训练成功证据或发布门禁。

## 3. 依赖与执行环境

建立 Python 实现时，以 `pyproject.toml` 管理元数据、构建配置与依赖，以纳入版本控制的 `uv.lock` 固定解析结果。运行设备默认只安装所需依赖，GPU 训练依赖按实际验证范围声明。Python、uv 及支持平台版本随真实验收确定，不预设宽泛兼容矩阵。

CI 和正式实验检查锁文件一致性并按锁安装；升级依赖同时更新锁文件，说明对运行、打包和旧实验的影响。锁文件不足以固定驱动、内核、构建选项和硬件行为，相关信息随运行清单保存。

以下为未来 Python 工程的命令约定，只有定义 `dev` 组、安装工具并建立测试后才可执行；当前不属于已验证项目命令：

```bash
uv lock --check
uv sync --locked --group dev
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked pytest
```

测试路径由实际测试配置收集，不要求预建三个空测试目录。`--locked` 会在锁文件与元数据不一致时报错，`--frozen` 跳过该检查，因此默认采用前者。wheel 构建与干净安装验证在构建后端确定后补入同一命令入口。[uv 锁定与同步说明](https://docs.astral.sh/uv/concepts/projects/sync/)

## 4. 版本管理与变更审查

建立 Git 仓库后，以 `main` 为集成主线，使用短期主题分支；`feat/`、`fix/`、`exp/`、`docs/` 为可选命名前缀，不设长期 `develop`。一个变更围绕明确问题，避免混合依赖升级、指标重定义与训练策略变更。实验分支名不能代替确定的源码版本及运行记录。

进入 GitHub 协作后，通过 PR 留存变更目的、范围、验证命令与实际结果、指标/数据/权限/支持范围影响，以及已知限制和必要回退方式。影响研究结论的修改另说明切分、分母、预算或 H 曝光是否变化。

在实际仓库支持的功能范围内，保护 `main` 不被强推或删除，要求有效的检查通过及审查讨论解决。单人阶段保留自审证据，不强制不存在的另一人批准；有稳定协作者后，对权限、schema、数据切分、指标和工作流要求独立审查。远端保护、CODEOWNERS 和报告渠道需按真实仓库及人员配置，不虚构已启用状态。

## 5. 三种验证各司其职

| 验证路径 | 内容 | 触发与数据边界 |
|---|---|---|
| 快速工程检查 | 静态检查、状态/来源/schema/工具/指标测试、打包与合成示例 | 本机开发及每个 PR；CPU、公开合成数据 |
| 真实后端验收 | 工具模板、parser、执行与恢复、模型加载、真实梯度更新及导出 | 后端或协议变化后受控执行，保存真实环境与结果 |
| 正式科研评价 | 独立任务收益、旧能力保持、成本、统计不确定性 | 冻结版本后按[评估协议](02_评估与统计协议_v0.5.md)运行，H 与开发反馈隔离 |

合成示例应有明确输入、预期输出和环境复位方法，覆盖有代表性的正常行动及失败恢复。工程检查通过仅支持对应实现正确性，不证明未见任务泛化、真实参数收益或硬件性能。普通 PR 不触发完整训练，公开 CI 不读取 H 或产生供调参使用的 H 反馈。

相关实现落地时，验证以下契约；修改这些行为须补齐有判别力的回归用例并运行已有相关检查：

- 撤回贯穿摘要和来源派生链，旧缓存不能重新激活要求；工具文本不能提升为直接用户授权。
- 未授权写操作在执行前被工具层阻止；缺参得到明确验证失败或询问，不能靠默认猜测使调用通过。
- parser 故障保存原始生成并归因，不直接变成已验证成功的正向训练目标；从真实状态核验的纠错续接仍按[数据协议](01_数据与状态协议_v0.4.md)使用。
- 完成判定关联真实工具结果和独立环境检查；伪造完成文本、空产物及部分成功不能被检查器计为完成。
- 无训练许可的数据不进入可训练集合；原始来源与派生样本不跨越规定集合，检查器及答案不进入待评估 Agent 工作区。

对模型的询问、引用结果等行为，另用真实后端任务验证，不用 mock 通过冒充模型行为成立。

## 6. Actions 与数据执行边界

启用 GitHub Actions 时，普通检查使用 `pull_request` 和 `permissions: contents: read`，仅在具体 job 有需要时增加权限。Action 引用固定到核验过来源的完整 commit SHA，并通过可审查的更新维护；若未来采用工作流依赖锁，核实支持范围与验证方式后替代重复机制。不将 PR 标题等外部文本直接拼接到 shell，不在持有 secrets 或写权限的上下文执行不可信 PR 代码。工作流变更属于重点审查对象。[GitHub Actions 安全说明](https://docs.github.com/en/actions/reference/security/secure-use)

本机和训练工作站不得作为执行公开不可信 PR 的通用 self-hosted runner。GPU 任务在已授权范围和固定提交上受控执行；正式部署按既有发布规则决定，Agent 不自行创造授权。以后确需远程自动执行，先落实独立数据权限、运行隔离与清理机制。[GitHub 自托管执行器说明](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners)

`AGENTS.md` 是开发助手指引，不是运行时 Instruction 库或安全机制。数据访问依赖实际权限，工具写操作依赖执行层授权，H 隔离依赖受控评估环境。私人轨迹仅在已授权目的与范围内访问，不进入公开提交或报告；文本约定和 `.gitignore` 不能替代这些控制。

## 7. 从结果追溯到运行与发布

运行记录的字段权威位置为[实验记录模板](05_实验记录模板_v0.4.md)，不另维护平行 schema。实现运行器时，将其中的一次运行记录保存为可解析清单，并关联冻结单、数据索引和产物；保存解析后的完整配置，包括默认值与命令行覆盖，不只保存配置路径。

确认性实验从干净、确定的提交运行。探索运行允许未提交修改，但保存基础提交、dirty 状态、差异及新增源码快照；没有 Git 的早期试跑保存源码清单与哈希，不声称已达到正式版本追溯要求。失败、恢复和未发布候选保留独立 run ID 及关联关系。

数据来源、授权、派生和删除使用[数据协议](01_数据与状态协议_v0.4.md)，划分与 H 曝光使用[评估协议](02_评估与统计协议_v0.5.md)，环境、导出与回滚使用[双机协议](03_双机运行与训练协议_v0.4.md)。大型对象在本地受控或外部版本化存储中保存，公开清单只含允许公开的元数据；保留检索位置、哈希、访问条件与保留策略。哈希不证明授权、正确性或长期可取得性。

分别管理软件版本、实验协议版本和模型产物版本。正式发布关联三者、具体 run ID、环境、评价证据、限制及回滚对象；仅引用 `main` 或附一个 checkpoint 不足以重建论文结果。

公开前确认原创材料权利归属及许可证，分别说明代码、文档、数据、底座与派生产物的许可，不直接沿用底座许可覆盖整个项目。公开发布时再填写真实作者与版本的 `CITATION.cff`、CHANGELOG、Release 和长期归档索引。许可证与署名尚未决定，当前不生成虚假文件。

## 8. 按实际阶段验收

当前阶段落实根规则、文件隔离、文档职责及运行记录要求。进入代码开发时，同步建立可安装包、依赖锁、代表性示例和关键自动检查；这些验收通过后，才将相应功能记为已实现或已验证。正式实验前验证清单生成、配置快照、来源隔离和检查器有效性，完成冻结并确定可重建的代码版本。

协作、真实训练、部署和公开发布分别增加其必要审查、验收及归档机制。多平台矩阵、自动发布、SBOM、复杂编排和多后端支持，只有出现可说明的需求后才引入。当前文档采用 planned、implemented、measured、independently_checked 描述研究证据阶段；不为套用另一模板再并列一套含义模糊的 validated 状态，未支持范围直接说明。

本规范借鉴科研软件的版本管理、自动测试及可复核示例实践；具体目录、工具和阶段安排是 CoEvo 的设计选择，不是文献规定的强制标准。[科研软件实践](https://journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1005510)
