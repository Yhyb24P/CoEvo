## 1. 设备分工与部署收敛

AMD 产品资料与 ROCm 兼容表只能支持硬件规格或列示环境，不能证明当前驱动、模型内核和吞吐。笔记本的 OS、驱动、功率模式、实装内存速率、核心线程调度和温度先记录。880M 使用共享内存，不能把 32GB RAM 当成另外附加 32GB 显存；工作站 CPU RAM 也不等于 GPU 可用容量。

阶段 A 使用 Qwen3.5-4B 原始权重，先在 5090 上安装实际兼容的高精度推理环境并接入 momo-code；vLLM 为当前安装起点，是否接受由实际原生工具与 128K+ 运行决定。短上下文 8K/16K 只作接口诊断。阶段 B/C 保持工作站运行，阶段 D 才合并、导出 GGUF、量化并比较笔记本 CPU/iGPU 后端。llama.cpp/Q8_0 为部署起点，具体量化与后端按实测确定；ROCm 等扩展不作为前置条件。

历史实施修订 `workstation-128k-2026-10-13` 已实测 momo-code 接入复用的 Pi SDK 文件 read/write。新任务沿用 Pi 执行机制，按 T01 场景需要扩展代码、文件和终端能力，并验证权限范围、工具失败、会话续接与真实结果记录；上游通用 CLI 和扩展尚未验收，不维护两套 Agent。上游模拟训练、评价和经验 A/B 路径从实际运行及发布决策中禁用，不能仅靠界面标识区分。首阶段由独立工具层授予指定目录、离线计算和 fixture 的操作能力；检查器与实验答案置于 Agent 不可修改的运行环境。笔记本断开工作站后仍应能够完成基本任务；不把工作站 fallback 的结果混入“笔记本独立运行”指标。

主模型若不满足工作站 E0 的原生工具或 128K+ 资格要求，可在排除模板/parser 缺陷后替换为同协议验证的模型，登记完整基线。不要等所有模型竞争完成才开始 E1；MiniCPM5-2B 的关键训练验证、Qwen3.5-9B 的冻结诊断均从剩余预算开展。

## 2. 运行冻结与正确性验证

冻结清单包括模型仓库 revision/文件 SHA-256、tokenizer、模板、parser、llama.cpp 与选定 Agent 的 commit、构建参数、schema、量化类型及转换器版本、Agent 策略、能力集合、缓存规则、采样参数和任务上限。Qwen3.5 默认思考模式，显式记录有效 `enable_thinking` 及思考 token；不能用界面开关名称代替实际提示和生成验证。

E0 的正确性序列为：已知正确调用直接送执行器 → 相同工具注入模板 → 保存模型原始生成 → 解析调用 → 参数语义与授权检查 → 真实执行 → 返回后的下一步 → 独立最终状态。每层都能分别记录失败，API 200 和 JSON 合法不作为端到端成功证据。

基线涵盖无工具、一个工具、相似函数、缺参、工具失败、空结果、部分写入、任务切换及明确撤回。覆盖 stream 与非 stream 的至少一次对照；正式首阶段采用一个冻结返回模式。暂不要求同时支持并行工具、所有 schema 或无限上下文。

当前工作站资格运行起点如下，具体后端参数与原始权重 revision 随真实入口固定；后续部署量化配置在 D 另列：

```yaml
model: Qwen/Qwen3.5-4B
precision: bf16
qualification_min_input_tokens: 131072
context_tokens: 139264
short_diagnostic_tokens: [8192, 16384]
enable_thinking: false
temperature: 0.7
top_p: 0.8
top_k: 20
min_p: 0.0
presence_penalty: 0.0
repetition_penalty: 1.0
concurrent_episodes: 1
parallel_tool_calls: false
max_generation_tokens: 384
max_episode_generated_tokens: 2048
max_tool_steps: 12
episode_timeout_seconds: 900
```

这些值不宣称最优，也不复制整组发布方推荐为科研事实。服务端若不支持某参数，记录有效值并在冻结前解决；工具返回需要预留上下文空间，超长任务切为有明确状态的多个阶段，不截掉决定动作所需的指令或结果。所有实验组使用同一相应上限，不能只给弱组额外重试。

128K+ 资格实际输入不少于 131072 token，服务上限另留生成和多轮工具返回空间；使用模型 tokenizer 和后端 usage 记录实际长度。信息定位覆盖前、中、后位置；多轮测试记录当前对象、指令变化与工具状态。不得通过截断或摘要压缩把资格输入缩短。OOM、超时或能力失败分别记录，不用 8K/16K 通过替代。阶段 D 再测笔记本短任务 p95、128K 填充时延、内存、交换和 OOM，原先 p95 ≤300s、保留约 8GiB 系统空间仅是待校准部署建议。记录总任务 p50/p95、TTFT、prefill/decode、实际 token、系统可用内存、进程 RSS、共享 GPU 内存、功耗与温度。共享内存计数可能重叠，不把 RSS 与 GPU reported bytes 直接相加。

CPU/iGPU 配对使用相同模型、量化、模板、提示、工具和预算；预热后随机化运行块，冷启动另报。主质量推断在统一工作站高精度后端完成，日常部署收益在笔记本配置另报，避免后端吞吐和工具解析差异混入参数收益。

## 3. 单卡训练起点

训练由独立本地组件执行，通过已核验候选数据、完整配置、运行清单与 checkpoint/Adapter 索引连接 Agent；修订 momo-code 的模拟训练入口以生成独立训练输入；当前训练调用由用户进行，替换随机评价和经验门禁为真实结果检查，不以 Tinker 服务或 `tinker://` checkpoint 代替 5090 本地训练。Transformers/PEFT 与 Unsloth 均为候选，选择依据是目标机器上的模块支持、mask 语义、真实梯度、吞吐和导出验收。

文本 BF16 LoRA 为主，不训练视觉塔、embedding/lm_head，不预设 QLoRA、RL 或权重 offload。Unsloth 当前文档为 Qwen3.5 提供 BF16 LoRA 和 GGUF 路线，同时警告 4-bit QLoRA 的量化差异；文档中的显存参考并非本卡保证。若使用标准 Transformers/PEFT 实现，先证明同样的参数、mask 和导出语义，而非因封装器更换重新开始模型竞赛。

建议校准配置：

```yaml
precision: bf16
adapter_type: lora
rank: 16
alpha: 32
dropout: 0.0
target_policy: supported_linear_modules_in_text_attention_and_ffn
exclude: [vision, embedding, lm_head]
optimizer: AdamW
learning_rate: 0.0001
weight_decay: 0.0
scheduler: cosine
warmup_ratio: 0.03
micro_batch_size: 1
gradient_accumulation_steps: 8
max_sequence_length: 4096
gradient_checkpointing: true
training_seeds: [17, 29, 43]
max_data_passes: 2
initial_supervised_token_cap: 200000
```

`target_policy` 是待展开的选择规则，不是可直接传给 PEFT 的模块名称。检查实际 `named_modules`、Qwen3.5 混合层投影与可训练参数，再保存展开后的模块列表和 hash。只写 `q_proj/v_proj` 或 `all-linear` 都不能代替检查；卷积、门控和状态参数是否训练需明确记录。主比较保持同一展开列表，架构覆盖扩展另作实验。

从少量正确样本做非发布的梯度冒烟，再校准统一的学习率、序列长度与预算。首先检查正确 Assistant 目标是否有非空 loss mask、有效梯度、有限 loss，以及预期 LoRA 参数是否变化。LoRA 初始化的某些因子首步梯度可为零，不能要求每个可训练张量每步都非零；也不能仅凭训练器写出 checkpoint 声称发生更新。

loss 按有效监督 token 聚合，梯度累积时检查权重是否保持一致，避免不同前缀/目标长度让每个 micro-batch 被无意赋予同等总权重。训练 mask 与统计的 B* 使用同一有效 token 定义；保存少量可审查的 token/role/mask 片段，不需要把全部敏感原文纳入日志。

正式共同监督预算 `B*` 在 D/L 中确定：不超过初始 200k 目标 token，不超过各主组可用正确数据在两次以内的目标量，并能在分配 GPU 时间内完成。若候选量不足，降低所有主组共同 B*，保留精度限制，禁止无记录重复少量来源“凑预算”。

预算不能同时被假定为相同监督 token、相同上下文 token、相同步数和相同 GPU 时间。主选择比较固定 B*、优化器与有效批量，按目标/前缀长度分层匹配，实际步数及前缀 token 单列；局部纠错的上下文/监督比可能更大，必须显式报告。等 GPU 时间分析对决定性比较补测，不能将计算差异隐藏在筛选收益里。

截断策略保护目标动作及其必要输入。跨 episode packing 必须隔离注意力与位置/损失语义，尤其不能假定混合架构支持普通 packing；未验证时禁用跨 episode packing。过长样本拆为独立状态前缀—正确动作窗口，记录舍弃条件与重建方法，不能任意保留尾部导致作用条件丢失。

### 3.1 当前退化诊断与训练控制（T04，初步诊断已开展）

已在 CPU 上复核旧六条候选：模板前缀对齐，总计 327 监督 token，全部只监督 write，不含 read、恢复或正常停止目标。工具重复与无效调用在退化轨迹中可见；这些只支持数据/行为假设，未确定因果原因。复现入口为 `coevo.diagnose`，详见[当前进度](../experiments/project-tasks/progress.md)。

后续核对 chat template/tool schema、token/role/loss mask、原始输出与 parser，并独立重载 Adapter 与 W0 比较。之后按匹配来源、监督 token 和预算比较当前局部写入目标与完整轨迹 SFT，分别诊断优化设置与模块覆盖，保留新能力和旧能力面板。一次候选退化尚不能确定是样本、优化还是加载问题；形成可信 SFT 基线或明确负结果后，再研究 Replay 和必要的抗遗忘方法。

当前 `awaiting_user_training` 是有意边界，尚未修改。用户已授权基础建设和有界 D 推理；尚未执行新训练。未来外部研究控制器可以按冻结策略调度训练、G 回归、接受/回滚及 episode 边界切换，但触发政策尚待确认。待评估模型只能提议，不得修改准入或发布规则；H 不用于周期选版。独立实验流与状态隔离要求见[数据协议](01_数据与状态协议_v0.4.md)，当前默认状态库与固定编号未满足多流隔离。

## 4. 周期更新、导出与回滚

ET 每组从原始 W0 开始训练。EL 则冻结基座，续训每组当前已接受的同一个 Adapter；各周期重新初始化优化器，数据混合与 replay 配额一致。不要一组累积 Adapter、另一组重训基座；也不无记录堆叠多个 Adapter。初始 replay 配额建议为监督 token 的 20%，在首周期前冻结，来自 L 的旧能力数据，不能来自 G/H。

发布产物为 `原始基座 + Adapter → 合并权重 → GGUF F16 → Q8_0`。保留 Adapter、配置、数据清单和原始基座，合并模型用于部署，不作为下周期续训的新隐藏基座。不同序列语义或量化必须各有版本。

验证顺序：

1. 高精度下，Adapter 模型与合并权重的已知提示 logits/输出行为配对；明确数值容差和采样差异。
2. GGUF F16 和 Q8 在冻结模板/parser 上跑相同原生工具任务，检查 EOS、终止与返回；Q6/Q4 仅对有必要的候选测。
3. 笔记本 G 回归与断开工作站任务通过后，按预定发布规则选择候选或保持上一版。

模板/parser 默认保留。确诊有缺陷需要修复时，修复后对所有受影响比较组统一重跑配对回归，登记版本影响；不能为每个模型单独改一套提示然后把差异归因于权重。

运行中使用模型、经验与策略的不可变快照；在 episode 边界切换接受版本。发布与实验记录均保存原始版本和上一版本的路径/hash，可回滚。G 的发布判断是适应性选择数据，不冒充 H 的科学确认。

阶段 A–C 的冷文件统一优先落在 `/mnt/e/CoEvo/{models,upstream,data,artifacts,runs,cache}`，项目用同名目录链接访问（cache 按配置指定）。活动代码与 `.venv` 保留 Linux 文件系统；若冷盘读取成为实际瓶颈，可有记录地暂存必要热文件，避免重复下载全量权重。

跨机闭环输入至少包括训练候选及来源/授权/核验清单、有效目标与 mask、完整配置、固定代码/依赖/模型引用；输出包括运行清单、失败日志、参数变化证据、Adapter、合并/导出索引及回归结果。字段复用[实验记录模板](05_实验记录模板_v0.4.md)，不另设平行运行 schema。Agent 只在 episode 边界装载接受版本；未通过发布规则则保留旧版。首条闭环在 A 的必要验收后开展，不等待 E1/ER 正式研究，且仅使用 L/D 数据；B 先验证训练、重新加载和工作站评价，导出与笔记本验收后移到 D。原 C 的三个周期保留为历史试点配方；新研究不直接继续合成三周期，先按 T00–T04 建立真实任务、反馈链与有效训练基线。Q1/Q2 并行建设，可比较版本后进入 R×W、同池交叉重训及独立任务流研究；周期数量本身不证明收益。此前用户已授权拉取源码、原始权重及安装训练推理环境；2026-10-13 当前要求暂停实施供云端研究确认，不自行恢复训练或周期运行。训练调用、真实场景与研究助手分工尚待确认；实际运行仍记录资源消耗，不扩大为无限训练或搜索。

评价优先直接使用 Harbor 的本地任务运行与验证接口，实际沙箱支持和隔离须验收。RSIGym 的任务提交、轨迹与候选审计接口作为组织参考，不将其 E2B/Tinker 云服务作为本地闭环依赖；上游 JobConfig 或结果格式通过薄适配连接。本机不具备容器资源时，仍可制作清单、经验/指标 CPU 检查及分析，重任务另行安排。

## 5. 资源上限与收缩规则

以下是首阶段**建议上限**，不是用户已承诺的耗时，也不是已实测费用。E0 测吞吐后可事前修订，修订需保留原预算与理由。

| 项目 | 5090 时间额度 | 优先用途 |
|---|---:|---|
| E0 训练链与校准 | 4 GPU-h | 冒烟、mask/梯度、导出；限制参数搜索 |
| ET 单轮主比较 | 24 GPU-h | 优先 T1/T2 三种子，余额 T3；失败消耗包含在内 |
| EL 三周期试点 | 30 GPU-h | 两组 × 三周期 × 两条学习流，共 12 次计划更新 |
| 交叉重训/定向诊断 | 6 GPU-h | 共享起点诊断、必要兼容性与等时间比较 |
| 生成、选择与集中评估 | 24 GPU-h | 固定/当前选择器、可核验续接与高精度任务评估 |
| **总计** | **88 GPU-h，其中训练 64 GPU-h** | 全部失败、重试与未发布候选计入 |

离线 CPU/iGPU 评估建议另设 120 设备小时；人工制作/复核建议先设 8 小时，并记录实际增量。一个训练 job 起始软上限为 2 GPU-h，EL 可按校准允许平均 2.5 GPU-h；实际额度以事前冻结清单为准。不能在看到某组不佳后单独增加预算。

若实测吞吐使全矩阵不可完成，依次取消完整跨模型训练、Q6/Q4/ROCm 扩展、T3 组件拆解和 EL 扩大；保留 E1、ER、T1/T2 与实际部署验证。若仍不足，明确把 ET/EL 标为试点并减少共同规模，而不是完成大量单种子分支。

每次运行日志记录实际全序列/监督 token、步数、目标来源数、显存 allocated/reserved 与 `nvidia-smi` 状态、吞吐、损失、梯度摘要、checkpoint/hash、失败与恢复。非正常中止和超预算候选保留，不把它们从“每次成功训练平均耗时”之外悄悄丢弃。
